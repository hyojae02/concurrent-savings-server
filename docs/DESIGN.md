# Concurrent Savings 설계 문서

## 1. 개요

Concurrent Savings는 정해진 정원까지만 신청을 받는 선착순 특판 적금 신청 시스템이다.

관리자 상품 등록 기능은 구현하지 않고, 특판 적금 상품 데이터는 시드데이터로 미리 구성한다. 프로젝트의 핵심 목표는 신청 요청이 동시에 몰리는 상황에서도 정원 초과 없이 신청을 처리하고, 이후 대기열, 멱등성, 비동기 처리로 안정적인 백엔드 흐름을 확장하는 것이다.

이 프로젝트는 기능의 양보다 백엔드 기본기 학습에 집중한다. 특히 동시성 제어, 데이터 정합성, 인덱스와 쿼리 튜닝, 캐싱, 분산 락, 비동기 처리, 부하 테스트, 배포까지 직접 경험하는 것을 목표로 한다.

## 2. 시작 계기

팀 프로젝트에서는 기능 구현 위주로 개발을 진행하면서 동시성 제어, 쿼리 튜닝, 인프라 운영처럼 백엔드 개발자가 반드시 이해해야 하는 영역을 깊게 다루기 어려웠다.

이를 보완하기 위해 개인 프로젝트로 선착순 특판 적금 신청 시스템을 설계한다. 단순 CRUD를 넘어, 동시에 들어오는 신청 요청을 어떻게 정합성 있게 처리할지, 병목은 어디에서 발생하는지, 어떤 방식으로 성능을 개선할 수 있는지를 직접 구현하고 검증한다.

## 3. 핵심 시나리오

1. 유저가 특판 적금 상품에 신청한다.
2. 상품의 잔여 정원이 있으면 신청은 즉시 성공 처리된다.
3. 정원이 소진된 경우 신청은 대기 상태로 등록된다.
4. 동일 유저가 같은 상품에 중복 신청하는 것은 차단한다.
5. 신청 결과는 `SUCCESS`, `WAITING` 상태로 저장한다. 신청 기간 외 요청처럼 처리할 수 없는 요청은 신청 데이터를 만들지 않고 실패 응답으로 반환한다.
6. 2차 구현에서는 네트워크 재시도 등으로 같은 요청이 반복될 경우, 멱등성 키를 기준으로 기존 처리 결과를 반환한다.
7. 2차 구현에서는 신청 결과 알림을 비동기로 처리하여 신청 API의 응답 지연을 줄인다.
8. 2차 구현에서는 취소 또는 이탈이 발생하면 대기열의 다음 유저를 순차적으로 승격한다.

## 4. MVP 범위

초기 MVP에서는 선착순 신청 처리와 정원 초과 방지를 우선 구현한다.

MVP에 포함하는 기능은 다음과 같다.

- 유저 시드데이터 구성
- 특판 적금 상품 시드데이터 구성
- 상품 조회 API
- 상품 신청 API
- 신청 단건 조회 API
- 상품별 신청 목록 조회 API
- 정원 내 신청 성공 처리
- 정원 초과 시 `Application.status = WAITING` 처리
- 동일 유저의 중복 신청 방지
- 동시 요청 상황에서 정원 초과가 발생하는 문제 재현
- 비관적 락을 이용한 정합성 보장

다음 기능은 2차 범위로 분리한다.

- 별도 `WaitQueue` 테이블
- 취소 발생 시 대기열 승격
- Redis 기반 대기열
- Redisson 분산 락
- 멱등성 키 처리
- 비동기 알림
- k6 부하 테스트
- AWS EC2 배포

## 5. 핵심 엔티티 초안

### User

신청자를 나타내는 엔티티다.

주요 필드:

- id
- name
- email
- created_at
- updated_at

### SavingsProduct

특판 적금 상품을 나타내는 엔티티다. 상품은 관리자 API 없이 시드데이터로 초기화한다.

주요 필드:

- id
- name
- interest_rate
- capacity
- remaining_capacity
- start_at
- end_at
- created_at
- updated_at

`remaining_capacity`는 동시성 제어 학습을 위해 사용한다. 초기 구현에서는 단순 차감 방식으로 동시성 문제를 재현하고, 이후 비관적 락과 분산 락을 적용해 정합성을 보장한다.

### Application

유저의 상품 신청 내역을 나타내는 엔티티다.

주요 필드:

- id
- user_id
- product_id
- status
- idempotency_key (2차 구현)
- applied_at
- created_at
- updated_at

상태값:

- SUCCESS
- WAITING
- FAILED
- CANCELED

MVP에서는 `SUCCESS`와 `WAITING`을 저장 상태로 사용한다. 신청 기간 외 요청은 신청 데이터를 생성하지 않고 실패 응답으로 처리한다. `FAILED`, `CANCELED`는 후속 기능에서 확장한다.

동일 유저가 같은 상품에 중복 신청하지 못하도록 `(user_id, product_id)` 유니크 제약을 둔다.

### WaitQueue (2차 구현)

정원 초과 후 대기 상태가 된 신청자의 순서를 관리한다.

MVP에서는 별도 대기열 테이블을 만들지 않고, `Application`의 `WAITING` 상태와 `applied_at` 기준으로 대기 상태를 표현한다. 2차 구현에서 별도 DB 테이블 또는 Redis 기반 큐로 분리한다.

주요 필드 후보:

- id
- product_id
- user_id
- application_id
- queue_order
- status
- created_at

상태값 후보:

- WAITING
- PROMOTED
- CANCELED

## 6. 정원 처리 정책

특판 적금 상품은 정해진 정원까지만 즉시 신청 성공 처리된다.

처리 규칙은 다음과 같다.

1. 신청 기간이 아니면 신청 데이터를 생성하지 않고 실패 응답을 반환한다.
2. 동일 유저가 이미 신청한 상품이면 중복 신청으로 차단한다. 이때 클라이언트가 기존 신청을 다시 조회할 수 있도록 실패 응답에 기존 `applicationId`를 함께 반환한다.
3. 잔여 정원이 있으면 `remaining_capacity`를 차감하고 신청 상태를 `SUCCESS`로 저장한다.
4. 잔여 정원이 없으면 신청 상태를 `WAITING`으로 저장한다.
5. MVP에서는 별도 대기열 테이블 없이 `Application.applied_at` 오름차순으로 대기 순서를 판단한다. 동시 신청으로 `applied_at`이 같은 경우를 대비해 `Application.id` 오름차순을 2차 정렬 기준으로 둔다.
6. 어떤 경우에도 `SUCCESS` 상태의 신청 수는 상품 정원을 초과할 수 없다.
7. MVP에서는 대기 등록 수에 상한을 두지 않는다. 대기열 상한 정책은 2차 구현에서 검토한다.

## 7. 동시성 정합성 포인트

이 프로젝트의 핵심 학습 목표는 동시에 들어오는 신청 요청을 정합성 있게 처리하는 것이다.

주요 정합성 포인트는 다음과 같다.

### 잔여 정원 차감

여러 요청이 동시에 같은 상품의 `remaining_capacity`를 읽고 차감하면 정원보다 많은 신청이 성공할 수 있다.

초기 구현에서는 이 문제를 테스트로 재현한다. 이후 MySQL 비관적 락을 적용하여 동일 상품에 대한 신청 처리 구간을 직렬화한다.

### 중복 신청 방지

동일 유저가 같은 상품에 여러 번 신청할 수 없도록 `(user_id, product_id)` 유니크 제약을 둔다.

애플리케이션 레벨에서 먼저 중복 여부를 확인하되, 최종 방어선은 DB 유니크 제약으로 둔다.

### 멱등성 처리 (2차 구현)

클라이언트 재시도나 네트워크 문제로 같은 신청 요청이 여러 번 도착할 수 있다.

2차 구현에서는 요청마다 `idempotency_key`를 받고, 이미 처리된 키라면 새 신청을 생성하지 않고 기존 결과를 반환한다.

### 대기열 순서 보장 (2차 구현)

정원 초과 신청은 대기 상태로 등록된다. MVP에서는 `Application.applied_at`을 기준으로 대기 순서를 판단한다.

동시 신청 상황에서는 여러 신청의 `applied_at`이 같은 값으로 저장될 수 있다. 이 경우 정렬 결과가 실행할 때마다 달라져 대기 순서를 검증할 수 없으므로, `(applied_at ASC, id ASC)`로 정렬 기준을 확정한다.

2차 구현에서는 별도 `WaitQueue` 테이블이나 Redis Sorted Set을 사용해 대기열 순서를 명확히 관리한다.

## 8. 비기능 요구사항

- 동시에 많은 신청 요청이 들어와도 정원을 초과한 성공 신청이 발생하지 않아야 한다.
- 중복 신청과 중복 요청이 데이터 정합성을 깨뜨리지 않아야 한다.
- 신청 API는 가능한 빠르게 응답해야 하며, 알림 같은 부가 작업은 비동기로 분리한다.
- 부하 테스트를 통해 병목 지점을 확인하고 HikariCP, 인덱스, 락 범위를 튜닝한다.
- 장애 상황에서도 신청 상태가 추적 가능해야 한다.
- 신청 기간 판정이 실행 환경의 시스템 타임존에 좌우되지 않아야 한다. 모든 시각은 UTC로 저장하고 API 응답에서 오프셋을 포함해 표현한다.
